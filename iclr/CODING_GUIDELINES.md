# ICLR 研究代码写法要求

适用于本研究后续新增代码与重构。目标：读者从上到下读一遍，就能知道输入是什么、每一步做什么、最后输出什么。简洁指逻辑直接，不是把代码挤成一行。

## 1. 不采用防御性编程

- 删除重复的类型、维度、空值、范围检查；不要在每层调用中反复验证同一件事。
- 不写为假想输入准备的多层 `if`、`getattr`、默认值、自动兼容和备用路径。写清本实验实际支持的数据结构和模型接口，直接使用。
- 不添加与算法无关的哈希、身份封装、通用校验框架和重复状态文件。
- 不捕获所有异常后继续运行，不吞掉 Traceback，不用零、空数组或默认值把失败伪装成有效结果。错误直接暴露，定位后修正。
- 钩子移除、文件关闭和GPU对象释放是必要的资源管理，不是兼容分支；集中写清楚。

## 2. 用空行区分逻辑，而不是压缩行数

一个逻辑步骤写一段，段落之间空一行；独立函数之间空两行。

一行只做一件事。禁止分号串联赋值、循环体和条件体；不写多层三元表达式、嵌套推导式或难以断点调试的长链式调用。

推荐的函数顺序：准备输入 → 核心计算 → 组织输出。不要把保存日志、兼容判断和数学运算交错在一起。

## 3. 命名直接说明含义

使用 `base_query`、`donor_query`、`candidate_keys`、`attention_weights`、`head_output` 等名字。

不用 `qd`、`kr`、`mo`、`sh`、`xx` 等需要反复查定义的缩写。公式附近可以用 Q、K、V，但必须说明张量轴的含义。

函数名说明动作，例如 `replace_query`、`compute_attention`、`compare_candidate_logits`。不用一个函数隐藏整套流程。

## 4. 函数短，结构平，不堆框架

一个函数只负责一个明确操作。复杂函数按实际步骤拆分，不为一行代码制造层层包装。

默认采用普通函数、明确参数和直接调用。没有实际需要，不添加基类、工厂、注册器、装饰器或“万能”工具层。

Q替换、K替换、V替换应能直接看出各自改了什么、保留什么，不能埋在几十种模式混杂的大分支中。

## 5. 注释解释实验含义

函数开头用一两句说明用途；只在必要处写清张量形状、token位置和对应公式。

注释回答“为什么这样做、改变了什么”，不重复代码字面意思，不用长篇术语说明遮盖不清楚的实现。

例如：

```python
# 使用另一份输入的查询，保留原输入的证据地址和内容。
query = donor_query

# 重新计算当前head读取哪些位置。
attention_logits = query @ base_keys.T * attention_scale
attention_weights = attention_logits.softmax(dim=-1)

# 读取原材料中的内容，交回模型继续计算。
head_output = attention_weights @ base_values
```

## 6. 重构与验证边界

可读性重构不偷偷改变公式、干预范围、评分方向、样本范围和已有结果；方法修改另行明确说明。

索引对齐、无未来信息、同世界替换等科学有效性检查集中在独立测试或校验步骤，不散落进核心算法。测试只保留会影响实验解释的关键行为，不为防御分支堆测试。

运行命令不使用 `set -e`，不后台运行，保留终端报错。复用既有缓存，不为了整理代码要求重跑无关的大模型实验。

交付说明简短回答：改了哪里、如何运行、实际验证了什么。没有跑过的模型或数据，不声称已经验证。
